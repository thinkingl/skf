# C*Core UKey 接口交互协议

> 文档性质：基于对厂商 x86-64 `libskf.so` 的逆向、`SG_IO` 抓包和原生实现的
> 交叉验证整理，不是厂商官方协议规范。
>
> 适用设备：`02e3:0702`，产品字符串 `CCore USB CCID DEVICE`，实测固件
> `1.24`、序列号格式见下。不同固件/型号可能存在差异。
>
> 本文档不包含设备认证密钥、用户 PIN、容器私钥或任何实际密钥 material。
> 示例中的 `<SERIAL>`、`<DEV_AUTH_KEY>`、`<PIN>` 均为占位符。

## 2. 协议分层

可以把该 UKey 的交互看成下面几层。它并不是 TCP/IP，但分层方式类似：
下层只负责搬运字节，上层才解释命令和对象。

```text
+--------------------------------------------------------------+
| 应用层：SKF API / 应用、容器、文件、PIN、密钥对象              |
+--------------------------------------------------------------+
| 命令层：APDU（CLA INS P1 P2 Lc Data）                         |
+--------------------------------------------------------------+
| 会话层：握手、设备认证、当前 DF/EF、PIN 登录状态              |
+--------------------------------------------------------------+
| 帧层：DEMO + 长度 + 模式 + magic + APDU                       |
+--------------------------------------------------------------+
| 传输层：USB Mass Storage vendor SCSI，SG_IO，512 字节块        |
+--------------------------------------------------------------+
| 物理层：USB 2.0 / USB CCID 复合设备（实际走 vendor SCSI）       |
+--------------------------------------------------------------+
```

实测该设备虽然产品字符串包含 `CCID`，但 SKF 接口不是通过 PC/SC APDU
传输，而是通过 `/dev/sgN` 的 vendor SCSI 命令读写 512 字节帧。原生实现
因此直接使用 Linux `SG_IO`。

---

## 3. 传输层

### 3.1 设备节点

Linux 下设备表现为 SCSI generic 节点：

```text
/dev/sg0
/dev/sg1
...
```

识别方式：读取

```text
/sys/class/scsi_generic/sgN/device/vendor
```

其内容包含 `C*CORE` / `C*Core` / `CCore`。也可以从块设备
`/sys/block/sdX/device/scsi_generic/` 找到对应 `sgN`。

### 3.2 SCSI 命令

| 方向 | CDB | 说明 |
| --- | --- | --- |
| 主机 → 设备 | `C0 00 00 02 00 ...` | 写 512 字节帧 |
| 设备 → 主机 | `C1 00 00 02 00 ...` | 读 512 字节帧 |

实测每次 `SG_IO` 传输固定 512 字节，CDB 长度为 16 字节。CDB 第 4 字节
（偏移 3）为 `0x02`，与 512 字节传输对应；实现中按 256 字节单位计算：

```c
cdb[0] = write ? 0xC0 : 0xC1;
cdb[3] = (transfer_len + 255) / 256;
```

`SG_IO` 的 `dxfer_len` 为 512，`timeout` 厂商实现约为 10 ms（读）/
200 ms（写），原生实现使用 3000 ms 以兼容慢速设备。

### 3.3 读写的原子性

一次命令由“写一帧 + 读一帧”组成。设备返回的帧可能不是当前命令的响应，
而是上一命令的延迟响应；上电/复位后的第一次读也可能返回旧数据。因此
实现应当在连接时先做握手并丢弃无效帧，而不是假设第一次读就是有效响应。

## 4. 链路握手

### 4.1 目的

握手用于确认设备处于 vendor SCSI 模式，并让设备进入可接收命令的状态。
它不进行密钥认证；真正的设备认证是后面的 `00 82` 命令。

### 4.2 实测流程

1. 从设备读 512 字节，记为 `R0`。该内容可能是上一次会话残留的响应。
2. 构造 512 字节 `W`：
   - `W[0..7] = "checking"`（ASCII，8 字节）
   - `W[8..15] = challenge[8]`，实现中使用
     `AA BB CC DD 11 22 33 44`
   - `W[16..511]` 可以保留 `R0` 的剩余内容，也可以清零。
3. 向设备写 `W`。
4. 从设备读 512 字节，记为 `R1`。
5. 校验：
   - `R1[0..7] == "checking"`
   - `R1[8+i] == ~challenge[i]`，`i = 0..7`

即设备把 8 字节 challenge 按位取反后回显。

### 4.3 注意事项

- 握手期间出现 SCSI `status=2` / `driver=8` 等错误并不一定表示设备损坏；
  厂商库在握手阶段会重试。
- 不要在握手未完成时发送 APDU。
- 握手完成后，所有命令都使用下一节的帧格式。

## 5. 帧层

### 5.1 请求帧

每帧固定 512 字节，前 16 字节为帧头，后面是 APDU。

```text
偏移  长度  字段            说明
0     4     "DEMO"          固定 magic
4     4     BE32 frame_len  帧长度字段
8     4     mode            普通命令为 00000000；加密/密钥命令为 ABCD5678
12    4     magic           固定 12345678
16    ...   APDU            命令数据
```

`frame_len` 的实测语义：

```text
frame_len = 8 + APDU_data_len
          = APDU 总长度（APDU 头 8 字节 + APDU 数据）
```

例如：

- 选择文件：APDU 数据 2 字节，APDU 总长 10，`frame_len = 0x0000000A`。
- 读 256 字节：APDU 数据 256，APDU 总长 264，`frame_len = 0x00000108`。
- `WriteKey`：APDU 数据 44，APDU 总长 52，`frame_len = 0x00000034`。

`mode` 的取值：

| mode | 用途 |
| --- | --- |
| `00000000` | 普通命令 |
| `ABCD5678` | 加密/密钥命令，例如 `80 5B`、`80 AE`、`80 B4` |

`mode` 位于帧偏移 8，`magic` 位于帧偏移 12。注意不要把 `mode` 和
APDU 内部的长度字段混淆。

### 5.2 APDU 格式

APDU 位于帧偏移 16，格式固定为 8 字节头 + 数据：

```text
APDU 偏移  长度  字段
0          1     CLA
1          1     INS
2          1     P1
3          1     P2
4          4     BE32 Lc
8          Lc    Data
```

因此：

```text
APDU 总长度 = 8 + Lc
frame_len   = 8 + Lc
```

`Lc` 只表示 Data 字段长度，不包含 8 字节 APDU 头，也不包含帧头。

### 5.3 普通响应帧

普通命令（选择、读、写、创建、删除等）的响应：

```text
偏移  长度        字段
0     4           "DEMO"
4     4           BE32 total
8     4           回显请求的 CLA INS P1 P2
12    4           固定 87 65 43 21
16    data_len    Data
16+data_len 2     SW1 SW2
```

其中：

```text
total = data_len + 2
```

即 `total` 只统计 Data + SW，不包含 8 字节响应头。实现读取响应时：

```text
SW        = resp[16 + data_len .. 16 + data_len + 1]
data_len  = BE32(resp + 4) - 2
Data      = resp[16 .. 16 + data_len - 1]
```

实测例子：

```text
44 45 4d 4f  00 00 00 26  00 a4 00 00  87 65 43 21
6f 1f ... 00 00 90 00
```

这里 `total=0x26=38`，所以 `data_len=36`，SW 位于偏移 52。

### 5.4 状态优先响应帧

部分命令不使用普通响应格式，而是把 SW 放在数据长度之前：

- `00 82` 设备认证
- `80 5B` SM1 设备密码
- `80 AE` 对称密钥
- `80 B4` 其他加密/密钥命令

格式：

```text
偏移  长度        字段
0     4           "DEMO"
4     4           固定 00 00 00 02
8     4           回显请求的 CLA INS P1 P2
12    4           固定 87 65 43 21
16    2           SW1 SW2
18    2           保留 00 00
20    4           BE32 data_len
24    data_len    Data
```

实测：

```text
44 45 4d 4f  00 00 00 02  00 82 00 00  87 65 43 21
90 00 00 00 00 00 00 10  <16 字节 data>
```

实现读取时：

```text
SW       = resp[16..17]
data_len = BE32(resp + 20)
Data     = resp[24 .. 24 + data_len - 1]
```

### 5.5 响应头 magic

普通请求和响应都包含：

```text
请求 magic: 12 34 56 78
响应 magic: 87 65 43 21
加密模式:   AB CD 56 78
```

这些 magic 用于快速识别帧类型和方向。原生实现会校验 `DEMO`、响应
magic 和长度范围；如果不匹配，返回 `SAR_FAIL`。

## 6. 状态字与错误映射

### 6.1 常见 SW

| SW | 含义 | SKF 映射 |
| --- | --- | --- |
| `9000` | 成功 | `SAR_OK` |
| `6A82` | 文件不存在 | `SAR_FILE_NOT_EXIST` |
| `6A83` | 记录不存在 | `SAR_FILE_NOT_EXIST` |
| `6A84` | 空间不足 | `SAR_NO_ROOM` / 参数错误 |
| `6A86` | P1/P2 错误 | `SAR_INVALIDPARAMERR` |
| `6A89` | 文件已存在 | `SAR_FILE_ALREADY_EXIST` |
| `6D00` | 不支持的命令 | `SAR_INVALIDPARAMERR` |
| `6982` | 安全状态未满足/未登录 | `SAR_USER_NOT_LOGGED_IN` |
| `6983` | PIN 已锁定 | `SAR_PIN_LOCKED` |
| `63Cx` | PIN 错误，剩余 `x` 次 | `SAR_PIN_INCORRECT`，`retry=x` |
| `6F01` | 参数/对象错误 | `SAR_INVALIDPARAMERR` |
| `6F0A` | 认证/安全校验失败 | `SAR_UNKNOWNERR` 或认证错误 |
| `6988` | 安全状态不满足、密钥未初始化或 MAC 校验失败 | `SAR_UNKNOWNERR` |
| `6A88` | 引用数据不存在/认证状态不对 | `SAR_UNKNOWNERR` |

`6F0A` 和 `6988` 在实测中经常表示“前置条件不满足”，而不是单纯的
“命令不存在”。例如：

- 未选择 `3F00` 就发 `00 82`，可能得到 `6A88`/`6F0A`。
- `WriteKey` 的 MAC IV 或密钥对象不对，得到 `6988`。
- PIN 连续错误会返回 `63Cx`，`x` 递减。

### 6.2 厂商内部错误

厂商库内部使用 `0xE000Dxxx` 错误码，再映射为 SKF 的
`0x0A0000xx`。例如：

```text
0xE000D041 -> 文件不存在
0xE000D042 -> 文件已存在
0xE000D043 -> 空间不足
```

原生实现不暴露这些内部码，直接返回 SKF 错误。

## 7. 会话与设备认证

### 7.1 设备状态

命令：

```text
80 B8 00 00 00000004 00000000
```

响应（普通格式）Data 为 4 字节状态，实测返回：

```text
00 00 00 01
```

该命令的完整语义尚未完全确认，但从调用时序看，它用于读取/设置设备的
安全状态或认证门控。厂商在创建设备对象时会先用它确认设备处于可操作
状态。

### 7.2 设备认证流程

设备认证使用 SM1 对 challenge 做加密，然后把密文交给 `00 82`。

#### 步骤 1：选择主文件

```text
00 A4 00 00 00000002 3F00
```

必须先选择 `3F00`。否则 `00 82` 可能返回 `6A88`/`6F0A`。

#### 步骤 2：生成 challenge

通过 `00 84` 从设备获取随机数。常用形式：

```text
00 84 00 00 00000008
```

响应数据 8 字节，记为 `R[8]`。把它放入 16 字节 challenge：

```text
challenge[0..7]  = R[0..7]
challenge[8..15] = 0x00
```

也可以直接生成 16 字节；但实测常用 8 字节随机 + 8 字节零。

#### 步骤 3：设置 SM1 密钥

使用 `80 5B 00 01` 下发 SM1 密钥 blob，见第 10 节。

#### 步骤 4：加密 challenge

使用 `80 5B 00 00`：

```text
80 5B 00 00 00000018
00 00 00 00 00 00 00 00
<16 字节 challenge>
```

响应为状态优先格式，Data 为 24 字节：

```text
00 00 00 00 00 00 00 00
<16 字节 ciphertext>
```

#### 步骤 5：发送认证

```text
00 82 00 00 00000010
<16 字节 ciphertext>
```

响应为状态优先格式：

- `SW=9000`：认证成功。
- `SW=63Cx`：失败，设备认证重试计数减少。
- `SW=6A88` / `6F0A`：前置状态或 challenge 不正确。

#### 重要约束

实测设备会把“最近一次 `00 84` 随机数”与后续认证/密钥命令关联。因此：

- 在 challenge 加密完成到 `00 82` 之间，不要再发 `00 84`。
- `WriteKey` 的 MAC IV 也来自紧邻其前的 `00 84`，中间不能插入其他
  `00 84`。
- 设备认证失败会计数；不要用错误报文反复试探，以免触发锁定。

### 7.3 设备认证状态机

```text
CONNECTED
   |
   | 选择 3F00 + 80 5B 设置 SM1 密钥
   v
SM1_READY
   |
   | 00 84 生成 challenge + 80 5B 加密 + 00 82 认证
   v
AUTHENTICATED
   |
   | 创建应用 / 写应用列表 / WriteKey 等
   v
OPERATIONAL
```

`AUTHENTICATED` 是连接级状态。断开重连后通常需要重新认证。部分命令
只需要应用级 PIN 登录，不需要设备认证；但创建/删除应用、写应用列表、
`WriteKey` 等管理命令需要设备认证。

## 8. 设备信息命令

### 8.1 读取打包设备信息：`80 AA 01 00`

请求：

```text
80 AA 01 00 00000000
```

响应 Data 为一段打包信息，实测开头：

```text
00 00 01 00
"C1106 UKEY 3302 1.24 20170426 V2C1106 CCM3302 CRYPT2 ***********"
...
```

可解析出的字段包括：

- 产品/厂商字符串
- 标签 `UKEY`
- 固件版本 `1.24`
- 序列号长度和序列号
- 容量、算法能力等

厂商库把序列号放在打包信息中；序列号本身是 8 字节 BCD/二进制混合：

```text
34 30 48 35 32 04 4F 43
```

显示为：

```text
3430483532044F43
```

### 8.2 读取序列号：`80 B9 00 00`

请求：

```text
80 B9 00 00 00000010
```

响应 Data 至少 8 字节：

```text
34 30 48 35 32 04 4F 43 00 00 00 00 00 00 00 00
```

前 8 字节就是设备序列号。注意第 6 个字节可能是 `0x04` 这样的控制字节，
不是纯 ASCII；做显示时按 `%02X` 拼接，不要直接当字符串。

### 8.3 读取容量：`80 B7 00 00`

请求：

```text
80 B7 00 00 00000008
```

响应 Data：

```text
BE32 total_space
BE32 free_space
```

实测：

```text
0001C3E0 0001AB80
```

即总空间 115680，剩余 108480。

### 8.4 设备状态：`80 B8 00 00`

见 7.1。

## 9. 文件系统模型

### 9.1 文件 ID 空间

实测使用 16 位文件 ID：

| ID | 用途 |
| --- | --- |
| `3F00` | 主文件 MF |
| `3F02` | 设备信息/标签相关 EF |
| `3F03` | 应用列表 EF（256 字节） |
| `2000` | 默认应用相关文件 |
| `2001` | 应用 PIN 文件 |
| `2002` | 应用文件目录 EF（477 字节） |
| `2F01..2Fxx` | 应用普通文件数据 EF |
| `1101..1105` | 容器名 EF |
| `1201..1205` | 容器相关 EF（推断） |
| `1301..1305` | 容器密钥 EF（推断） |
| `1401..1405` | 容器加密证书 EF（按槽位） |
| `1501..1505` | 容器签名证书 EF（按槽位） |
| `3000..9000` | 应用 DF，步长 `0x1000` |

`DEFAULT` 应用是隐式的，通常使用 `0x2000`，不写入应用列表。

### 9.2 选择文件：`00 A4`

请求：

```text
00 A4 P1 00 00000002 <file_id_be16>
```

`P1` 的实测语义：

| P1 | 用途 |
| --- | --- |
| `00` | 普通选择，返回 FCI |
| `01` | 选择父文件/返回父级 FCI（用于创建前探测） |
| `02` | 选择 EF 以便读/写，返回 FCI |

响应为普通格式，Data 是 FCI（文件控制信息）。

### 9.3 读二进制：`00 B0`

请求：

```text
00 B0 P1 P2 000000L
```

其中 `P1 P2` 是 16 位偏移，`L` 是读取长度。帧的 APDU 数据区还要附带
`L` 个零字节作为读缓冲区占位：

```text
APDU = 00 B0 P1 P2 000000L  +  L 字节 00
```

响应 Data 为实际读到的字节，SW 在普通响应末尾。若请求超过文件剩余
长度，设备返回实际可用长度；实现应按返回长度更新 `outlen`。

### 9.4 写二进制：`00 D6`

请求：

```text
00 D6 P1 P2 000000L
<L 字节数据>
```

`P1 P2` 为 16 位偏移。实测写文件、写目录、写应用列表都使用
`P1=0, P2=0`。偏移非零时的行为应按 `P1 P2 = BE16(offset)` 处理，
但尚未覆盖所有边界。

### 9.5 创建文件：`80 E0`

请求：

```text
80 E0 <file_id_be16> 000000<attr_len>
<attr_len 字节属性>
```

`file_id` 在 APDU 的 P1/P2 中，不在属性里；属性长度常见为 12 或 24。

### 9.6 删除文件：`80 E4`

请求：

```text
80 E4 00 00 00000002 <file_id_be16>
```

删除成功返回 `9000`。删除应用 DF 也会删除其子文件。

### 9.7 FCI 格式

选择 EF 后返回的 FCI 实测示例：

```text
6F 17
  80 02 <size_be16>
  82 01 01
  83 02 <file_id_be16>
  86 04 0F 0F 00 00
  85 04 FF FF FF FF
  00 00
```

字段：

| Tag | 含义 | 说明 |
| --- | --- | --- |
| `6F` | FCI 外层 | 长度 1 字节 |
| `80` | 文件大小 | 2 字节 BE16 |
| `82` | 文件类型/状态 | 常见 `01` |
| `83` | 文件 ID | 2 字节 BE16 |
| `86` | 访问属性 | 常见 `0F 0F 00 00` |
| `85` | 权限/标志 | 常见 `FF FF FF FF` |

`SKF_GetFileInfo` 主要从 `80` 取 `FileSize`，从 `85`/应用层记录取权限。

## 10. 设备密码与密钥对象

### 10.1 SM1 设备密码：`80 5B`

`80 5B` 使用“状态优先响应帧”，并且帧模式为 `ABCD5678`。

#### 设置密钥：`80 5B 00 01`

请求数据 72 字节：

```text
random[8]
DES-CBC(
    key = random[8],
    IV  = serial[0..7],
    data = SM1_key[16] || 00 * 48
)
```

即：

```text
blob = R[8] || DES-CBC(R, serial[0..7], K[16] || 0^48)
```

APDU：

```text
80 5B 00 01 00000048 <72 字节 blob>
```

设备保存该 SM1 密钥，后续 `80 5B 00 00` 使用它。

#### 加密：`80 5B 00 00`

请求数据 24 字节：

```text
00 * 8 || plaintext[16]
```

APDU：

```text
80 5B 00 00 00000018 00*8 <16 字节明文>
```

响应 Data：

```text
00 * 8 || ciphertext[16]
```

实现只取最后 16 字节作为密文。

### 10.2 控制密钥

应用密钥对象使用一个“控制密钥”作为第一层保护。它不是设备认证密钥，
而是从设备序列号派生的：

```text
serial_buf[0..7]  = 设备序列号 8 字节
serial_buf[8..11] = 00 00 00 00
control_key[16]   = MD5(serial_buf[0..11])
```

注意只取 12 字节做 MD5。实测序列号 `34 30 48 35 32 04 4F 43` 时，
控制密钥为 `MD5(34 30 48 35 32 04 4F 43 00 00 00 00)`。

### 10.3 写密钥对象：`84 A5 02`

请求：

```text
84 A5 02 P2 0000002C
<40 字节密文>
<4 字节 MAC>
```

- `P2=01`：应用密钥对象（app key）
- `P2=00`：PIN 对象

#### 明文布局（40 字节）

```text
00 00 00 1C
<28 字节对象>
80
00 * 7
```

即：4 字节长度字段（固定 `0x1C`）+ 28 字节对象 + `0x80` 填充到 40 字节。

#### 加密

- 第一次写：使用 `control_key`。
- 后续写：使用第一次对象中携带的 16 字节 app key。
- 算法：`3DES-ECB(K, plaintext[40])`，双密钥展开为 `K1||K2||K1`。

#### MAC

MAC 输入为：

```text
84 A5 02 P2 00000028
<40 字节密文>
```

注意 MAC 输入中的长度字段是 `0x28`（40），不是最终 APDU 的 `0x2C`。

MAC 计算：

```text
M = single-DES-CBC-MAC(
        key = K1,
        IV  = 最近一次 00 84 返回的 8 字节随机,
        data = MAC 输入 || 80 || 00 填充到 8 字节边界)

final = E_K1(D_K2(M))
MAC   = final[0..3]
```

设备端使用同一次 `00 84` 随机作为 IV，因此 `WriteKey` 之前必须紧邻
一次 `00 84`，中间不能插入其他 `00 84`。

最终 APDU 数据长度为 44，APDU 总长为 52，帧长度字段为 `0x34`。

#### 对象格式

实测创建应用时写入三个对象。

**对象 1：应用密钥对象（P2=01）**

```text
偏移  值        说明
0     11        对象类型
1     01
2     12        算法/对象类别
3     00
4     0F
5     F0
6     00
7     06        PIN 长度（示例）
8     10        数据长度 16
9..11 00
12..27        16 字节 app key 随机数
```

对象 1 的 16 字节随机数同时成为后续 `P2=00` 对象的加密密钥。

**对象 2：管理员 PIN 对象（P2=00）**

```text
偏移  值        说明
0     12
1     01
2     12
3     04
4     0F
5     45
6     04
7     <admin_pin_len>
8     10
9..11 00
12..27        admin PIN，右侧补 0
```

**对象 3：用户 PIN 对象（P2=00）**

```text
偏移  值        说明
0     13
1     01
2     12
3     01
4     0F
5     25
6     03
7     <user_pin_len>
8     10
9..11 00
12..27        user PIN，右侧补 0
```

对象字段的精确语义（权限、用途、算法）部分仍是推断；实现时应以
实测值匹配为先，不要随意改字节。

### 10.4 修改设备认证密钥：`84 A5 01`

抓包观察到：

```text
84 A5 01 00 00000024
<36 字节数据>
```

该 36 字节数据的内部布局尚未完全反向。已知它不是普通 PIN 修改，
且需要设备已认证。本文档暂不给出字段表，避免误导。

## 11. PIN 管理

### 11.1 PIN 块加密

PIN 在发往设备前会被加密。实测算法：

```text
R[8] = 设备 00 84 返回的 8 字节随机

IV[8] = serial[8..11] || R[0..3]
K[8]  = DES-CBC(
           key = serial[0..7],
           IV  = IV,
           data = R[8]
        )

PIN_block[16] = PIN 字符串，右侧补 0
encrypted[16] = DES-ECB(K, PIN_block)
```

也就是说，随机数 `R` 不直接出现在报文中，设备通过“最近一次 `00 84`”
恢复它。所有 PIN 命令发出前都必须先生成这个随机数，且中间不要插入
其他 `00 84`。

### 11.2 验证 PIN：`00 20`

```text
00 20 P1 00 00000010 <encrypted[16]>
```

`P1`：

- `00`：用户 PIN
- `01`：管理员 PIN

成功返回 `9000`，并建立应用级登录状态。失败返回 `63Cx`，`x` 为剩余
重试次数；连续失败会返回 `6983`（锁定）。

### 11.3 修改 PIN：`80 5E`

```text
80 5E P1 00 00000028 <encrypted[40]>
```

明文 40 字节：

```text
old_pin[16] || FF || new_pin[16] || 00 * 7
```

`P1`：

- `01`：用户 PIN
- `00`：管理员 PIN

### 11.4 解锁 PIN：`80 2C`

```text
80 2C 00 00 00000020 <encrypted[32]>
```

明文 32 字节：

```text
admin_pin[16] || new_user_pin[16]
```

### 11.5 查询 PIN 信息：`80 BC`

原生实现使用 `80 BC`，参数块长度字段为 `0x0C`；响应 12 字节，常见字段：

```text
buf[7]  = max PIN length
buf[9]  = default PIN 标志（FF 表示未改/默认）
buf[11] = remaining retries
```

该命令的完整参数布局尚未完全确认，原生实现按上述偏移读取。

## 12. 应用管理

### 12.1 应用列表 EF `3F03`

应用列表是一个 256 字节的 EF。实测布局：

```text
偏移      长度  内容
0x00      16    记录 0 的应用名
0x10      2     记录 0 的应用 ID（LE16）
0x12      2     应用数量 count（LE16）
0x14      20    记录 1：应用名[16] + 应用 ID（LE16）+ 2 字节保留
0x28      20    记录 2
...
```

注意：

- `count` 位于 `0x12`，与记录 0 的尾部重叠；记录 0 实际只使用
  `0x00..0x11`。
- 记录 `k`（0-based）起始偏移为 `0x14 * k`。
- 应用 ID 使用 **小端序**。例如 KEDA 的字节是 `00 30`，值为 `0x3000`。
- 应用名最长 15 个字符，记录中补 0 到 16 字节。
- `DEFAULT` 不在列表里，由实现隐式加入。

应用 ID 分配：

```text
DEFAULT = 0x2000（隐式）
用户应用 = 0x3000, 0x4000, 0x5000, ..., 0x9000
```

最多 7 个用户应用。若所有候选 ID 都被占用，返回 `SAR_NO_ROOM`。

### 12.2 枚举应用

读取 `3F03` 的 256 字节，按 `0x12` 的 count 和上述记录布局解析，
并在返回列表开头加入 `DEFAULT`。返回格式为连续的 NUL 结尾字符串：

```text
"DEFAULT\0KEDA\0SKFAPP\0"
```

### 12.3 创建应用

实测完整流程（顺序很重要）：

1. 设备认证。
2. 选择 `3F00`，读取 `3F03` 应用列表。
3. 检查应用名是否已存在；若存在返回 `SAR_APPLICATION_EXISTS`。
4. 选择空闲应用 ID（`0x3000..0x9000`，步长 `0x1000`）。
5. 在列表中追加记录，写回 `3F03` 的 256 字节。
6. 创建应用 DF：

   ```text
   80 E0 <app_id> 00000018
   38 0F 0F 0F 0F 00 00 00 00 00 00 00
   00 00 00 00 00 00 00 00 00 00 00 00
   ```

7. 选择应用 DF，创建 PIN 文件 `2001`：

   ```text
   80 E0 20 01 0000000C
   D8 0F 0F 0F 00 10 00 30 00 03 00 00
   ```

8. 选择 `2001`（或确保当前 EF 为 `2001`）。
9. 通过 `00 84` 生成 16 字节 app key 随机数。
10. 生成对象 1，用 control key 执行 `WriteKey P2=01`。
11. 通过 `00 84` 生成 8 字节 MAC IV。
12. 生成对象 2/3，用 app key 执行 `WriteKey P2=00`（每次前都要
    新的 `00 84` MAC IV）。
13. 选择应用 DF，验证用户 PIN（`00 20`）。
14. 扫描 `1101..1105`，找到空闲容器槽。
15. 创建默认容器 `1101`：

    ```text
    80 E0 11 01 0000000C
    01 0F 0F 00 00 00 00 41 00 00 00 00
    ```

16. 选择 `1101`，写入容器名：

    ```text
    00 D6 00 00 00000008
    44 45 46 41 55 4C 54 00     ; "DEFAULT\0"
    ```

17. 返回应用句柄。

创建应用需要设备认证；未认证时返回 `SAR_USER_NOT_LOGGED_IN`。

### 12.4 删除应用

1. 设备认证。
2. 选择 `3F00`，读取 `3F03`。
3. 按应用名查找记录，取得应用 ID（LE16）。
4. 从列表中删除该记录，后续记录前移，count 减 1，空记录清零。
5. 写回 256 字节列表。
6. 选择 `3F00`。
7. 删除应用 DF：

   ```text
   80 E4 00 00 00000002 <app_id>
   ```

删除当前已打开的应用前应先断开/重连，避免当前 DF 状态干扰。

## 13. 容器管理

### 13.1 容器槽

实测每个应用最多 5 个容器槽：

```text
1101, 1102, 1103, 1104, 1105
```

每个容器至少包含：

- 容器名 EF：`110x`
- 容器密钥/证书相关 EF：`120x`、`130x`、`140x`、`150x`（具体用途
  部分为推断）

`DEFAULT` 容器创建在 `1101`，名称为 `DEFAULT`，长度 8（含 NUL）。

### 13.2 创建容器

1. 确保用户 PIN 已登录。
2. 选择应用 DF。
3. 扫描 `1101..1105`，选择每个文件，`6A82` 表示空闲。
4. 创建容器名 EF：

   ```text
   80 E0 11 0x 0000000C
   01 0F 0F 00 00 00 00 41 00 00 00 00
   ```

5. 选择该 EF（P1=2），写入容器名 + NUL。
6. 创建密钥 EF `13 0x`：

   ```text
   80 E0 13 0x 0000000C
   1A 23 23 00 00 00 00 68 00 00 00 00
   ```

7. 返回容器句柄。

容器名 EF 的大小属性为 `0x41`（65 字节），足以存放 64 字节名 + NUL。

### 13.3 删除容器

1. 选择应用 DF。
2. 按名称找到容器名 EF 的槽号。
3. 删除该槽对应的密钥/证书 EF（`130x`、`120x`、`140x`、`150x`）。
4. 删除容器名 EF `110x`。

### 13.4 容器类型

`SKF_GetContainerType` 返回：

```text
0  空容器（没有密钥 EF）
1  RSA 容器
2  ECC 容器
```

类型由容器密钥 EF `13xx` 的 FCI 决定：选择该 EF，解析
`80 02` 文件长度，长度为 `0x68`（104 字节）时是 ECC，否则是 RSA。
不是根据容器槽位推断；`DEFAULT` 在未生成密钥时类型为 0。

## 14. 应用文件系统

### 14.1 文件目录 EF `2002`

每个应用有一个 477 字节的文件目录 EF：`2002`。

创建目录 EF 的属性：

```text
80 E0 20 02 0000000C
01 0F 0F 0F 00 00 01 DD 00 00 00 00
```

其中 `01 DD` = 477。

目录初始内容：

```text
byte 0     = 0x00
byte 1..   = 0xFF
```

每创建一个文件，count 增加，新增目录项写入第一个 `0xFF` 区域。

### 14.2 目录项布局

目录总大小 477 字节：

```text
偏移 0       1 字节   文件数量 count
偏移 1       68 字节  目录项 0
偏移 1+68    68 字节  目录项 1
...
```

目录项（68 字节）实测布局：

```text
项内偏移  长度  内容
0x00      64    文件名，NUL 结尾，剩余补 0xFF
0x40      1     0xFF（保留/权限）
0x41      2     文件 ID，LE16
0x43      1     0x00（状态/保留）
```

例如文件名 `F1.TXT`、ID `0x2F01`：

```text
46 31 2E 54 58 54 00 FF ... FF  01 2F  00
```

最多文件数：

```text
1 + 7 * 68 = 477
```

因此一个应用最多 7 个普通文件。

### 14.3 创建文件

1. 选择 `3F00`，再选择应用 DF。
2. 尝试选择 `2002`；若返回 `6A82`，创建目录 EF 并初始化为
   `00 FF FF ...`。
3. 读取 477 字节目录。
4. 检查同名文件；若存在返回 `SAR_FILE_ALREADY_EXIST`。
5. 在目录中找空闲文件 ID（从 `0x2F01` 开始）。
6. 创建文件数据 EF：

   ```text
   80 E0 2F xx 0000000C
   01 0F 0F 00 00 00 00 <size> 00 00 00 00
   ```

   实测 `size` 放在属性第 7 字节（偏移 7），例如 16 字节文件为
   `... 00 10 00 00 00 00`，100 字节文件为 `... 00 64 00 00 00 00`。
   大于 255 字节时的布局尚未完全验证。

7. 选择 `2002`，写回更新后的 477 字节目录。

### 14.4 枚举文件

读取 `2002` 的 477 字节，按 count 遍历目录项，返回连续 NUL 结尾
文件名：

```text
"F1.TXT\0F2.BIN\0"
```

### 14.5 读取文件

1. 选择 `3F00`，再选择应用 DF。
2. 读取 `2002`，按名称找到文件 ID。
3. 选择文件 EF（P1=2）。
4. 发送：

   ```text
   00 B0 <offset_be16> 000000<len>
   <len 字节 00>
   ```

5. 响应 Data 为文件内容；`outlen` 更新为实际长度。

### 14.6 写入文件

1. 选择 `3F00`，再选择应用 DF。
2. 读取 `2002`，找到文件 ID。
3. 选择文件 EF（P1=2 或 0）。
4. 发送：

   ```text
   00 D6 <offset_be16> 000000<len>
   <len 字节数据>
   ```

5. 成功返回 `9000`。

### 14.7 获取文件信息

1. 按名称在 `2002` 中找到文件 ID。
2. 选择文件 EF（P1=0），取得 FCI。
3. 解析 `80 02 <size_be16>` 得到 `FileSize`。
4. 根据 `85 04` 和目录项填充权限字段。
5. `FileName` 使用调用方传入的名称或目录项名称。

### 14.8 删除文件

1. 选择 `3F00`，再选择应用 DF。
2. 读取 `2002`，找到文件 ID。
3. 选择文件 EF，发送：

   ```text
   80 E4 00 00 00000002 <file_id>
   ```

4. 从目录中删除该项，count 减 1，写回 477 字节目录。
5. 注意：目录项删除后，后续项前移，空区域补 `0xFF`。

### 15.5 导入、验签与 ECC 协商（原生实现扩展）

这一节描述原生库当前支持的导入/协商路径。它不是厂商完整加密信封
格式的替代规范；带 `原生扩展` 的字段是本地实现约定。

#### RSA 验签：`80 52` / `80 53`

`SKF_RSAVerify` 不直接用主机大数运算验证设备签名，而是把公钥模数和
指数设置到设备运算上下文，再让设备做公钥运算：

```text
80 52 01 B0 00000080 <128 字节模数，设备字节序>
80 52 02 B0 00000080 <128 字节指数>
80 53 00 80 00000080 <128 字节签名>
```

`80 53` 返回恢复出的 128 字节消息块。原生实现把摘要按 4 字节分组
反序放入消息块，与设备 `80 54` 的输入格式一致，然后比较整块。

主机侧还保留 raw RSA 回退，用于导入的软件 RSA 私钥。

#### 导入证书：每容器 `14xx` / `15xx`

证书 EF 是**按容器槽位**分配的，不是固定的 `1501/1502`：

```text
容器槽位 slot = 0x1101..0x1105
加密证书 EF   = 0x1401 + (slot - 0x1101)
签名证书 EF   = 0x1501 + (slot - 0x1101)
```

例如：

```text
slot 0x1101 (DEFAULT) -> enc 0x1401, sign 0x1501
slot 0x1102 (K01231)  -> enc 0x1402, sign 0x1502
slot 0x1103           -> enc 0x1403, sign 0x1503
```

`SKF_ImportCertificate` 创建对应 EF，属性长度 12 字节，证书长度写在
属性字节 `[6..7]`（大端），文件内容就是 X.509 DER 证书。

`SKF_ExportCertificate` 必须先选择应用 DF 和容器密钥 EF（`130x`），
再选择证书 EF，解析 FCI 的 `80 02` 得到文件长度，按该长度读取；不要
盲目按固定 0x1C1 读取，否则短证书会读越界、长证书会截断。

原生实现会校验证书公钥与容器公钥是否一致：RSA 比较模数，ECC 比较
X/Y 坐标；设备生成的不可导出 ECC 公钥通过容器密钥 EF 导出后比较。

#### 导入会话密钥：`SKF_ImportSessionKey`

原生实现接受 16/24/32 字节原始会话密钥：

```text
data = key[16]（SM4/SM1）
```

返回的句柄可直接用于 `SKF_Encrypt` / `SKF_Decrypt`。厂商库通常会先用
容器私钥解开会话密钥信封，这一步的原生实现暂未做。

#### 导入 RSA 私钥对：`SKF_ImportRSAKeyPair`

支持两种格式。

**标准 wrapped-key 格式**（容器内已有可用的软件 RSA 私钥）：

```text
pbEncryptedData = RSA PKCS#1 v1.5 加密的 16 字节会话密钥
pbWrappedKey    = SM4-ECB(会话密钥, RSAPRIVATEKEYBLOB 或 PKCS#1 DER)
ulSymAlgId      = SGD_SM4_ECB
```

导入时先用容器 RSA 私钥解密 `pbEncryptedData` 得到会话密钥，再用
`ulSymAlgId` 解密 `pbWrappedKey`。解密后的内容可以是完整的
`RSAPRIVATEKEYBLOB`，也可以是 PKCS#1 `RSAPrivateKey` DER。

**原生扩展格式**（无 wrapped 数据）：

```text
pbWrappedKey     = RSAPRIVATEKEYBLOB
ulWrappedKeyLen  = sizeof(RSAPRIVATEKEYBLOB)
pbEncryptedData  = NULL / 空
```

标准格式要求容器内已经有一个可用的软件 RSA 私钥（可通过原生扩展导入）；
由设备 `SKF_GenRSAKeyPair` 生成、不可导出的私钥目前还不能直接用于解密
标准信封。

#### 导入 ECC 私钥对：`SKF_ImportECCKeyPair`

支持两种格式。

**标准 `ENVELOPEDKEYBLOB` 格式**（容器内已有可用的软件 ECC 私钥）：

```text
ulSymmAlgID  = 会话密钥算法，通常 SGD_SM4_ECB
ulBits       = 256
PubKey       = 待导入 ECC 公钥
ECCCipherBlob:
    X/Y       = SM2 C1 临时公钥（存放在 64 字节坐标数组的低 32 字节）
    HASH      = SM2 C3 = SM3(x2 || M || y2)
    CipherLen = 16
    Cipher    = SM2 C2
cbEncryptedPriKey[32..63] = SM4-ECB(会话密钥, ECC 私钥标量)
```

处理流程：

1. 用容器 ECC 私钥对 `ECCCipherBlob` 做 SM2 解密，得到 16 字节会话密钥。
2. 用会话密钥和 `ulSymmAlgID` 解密 `cbEncryptedPriKey + 32`。
3. 从解密结果取 32 字节私钥标量，校验其公钥与 `PubKey` 一致。
4. 保存私钥和公钥到当前容器上下文。

SM2 解密使用：

```text
C1 = (XCoordinate[32..63], YCoordinate[32..63])
S  = d * C1
KDF = SM3(S.x || S.y || counter_be32)
M  = C2 xor KDF
C3 = SM3(S.x || M || S.y)
```

**原生扩展格式**：

```text
ECCCipherBlob.CipherLen = 0
cbEncryptedPriKey[0..31] = 32 字节 SM2 私钥标量
PubKey                   = 对应公钥
```

标准格式要求容器内已经有一个可用的软件 ECC 私钥；由设备
`SKF_GenECCKeyPair` 生成、不可导出的私钥目前还不能直接解密标准信封。

#### ECC 协商

原生实现使用 SM2 曲线 ECDH + SM3 KDF，流程如下：

1. 发起方容器 `c1` 调用

   ```text
   SKF_GenerateAgreementDataWithECC(c1, alg, &sponsorTemp, id1, len1, &hAgree)
   ```

   生成发起方临时密钥对，返回 `sponsorTemp` 和协商句柄。

2. 响应方容器 `c2` 调用

   ```text
   SKF_GenerateAgreementDataAndKeyWithECC(c2, alg,
       &sponsorPub, &sponsorTemp, &respTemp, id2, len2, id1, len1, &key2)
   ```

   生成响应方临时密钥对，返回 `respTemp`，并直接派生会话密钥。

3. 发起方调用

   ```text
   SKF_GenerateKeyWithECC(hAgree, &respPub, &respTemp, id2, len2, &key1)
   ```

   派生同一会话密钥。

共享秘密：

```text
shared = ECDH(static_priv_a, temp_pub_b)
       ^ ECDH(temp_priv_a, static_pub_b)
```

KDF：

```text
key[16] = SM3(shared || min(id_a,id_b) || max(id_a,id_b))[0..15]
```

ID 按长度和字节序排序，保证双方计算一致。

参与协商的两个容器都必须先通过 `SKF_ImportECCKeyPair` 导入 ECC
私钥；由设备 `SKF_GenECCKeyPair` 生成的容器私钥不导出，因此原生
实现暂不能直接用于该协商路径。

## 17. 安全与实现注意事项

1. **不要记录密钥/PIN 明文**。设备认证密钥、用户 PIN、app key、MAC IV
   都应视为敏感数据。
2. **PIN 重试计数**：`63Cx` 中的 `x` 是剩余次数；不要用错误 PIN 反复
   试探，否则会触发 `6983` 锁定。
3. **设备认证重试**：错误 challenge 也会计数。调试时应使用一次性临时
   应用和可重置设备，避免把生产密钥锁死。
4. **随机数关联**：`00 84` 的“最近一次随机数”被设备用于 PIN 加密、
   WriteKey MAC、设备认证 challenge。生成后必须立即用于对应命令，中间
   不要插入其他 `00 84`。
5. **应用列表和应用 ID 使用小端序**。这是实测最容易出错的地方之一。
6. **文件目录项和 FCI 的长度/偏移**必须按实际返回解析，不要假设固定
   总长度。
7. **状态优先响应**只用于少数命令；普通响应和状态优先响应的数据起始
   偏移不同，混用会导致“看起来命令成功但数据错位”。
8. **设备可能返回上一条命令的延迟响应**；连接后要先握手并丢弃无效帧。
9. **临时应用/容器测试后要清理**。创建应用会写应用列表、应用 DF、
   PIN 文件和默认容器；只删列表记录会留下孤儿文件。

## 18. 已知限制与待补充

以下内容尚未完全反向或未覆盖所有边界：

- `84 A5 01` 修改设备认证密钥的 36 字节数据布局。
- `80 AE` / `80 B4` 的完整对称密钥/MAC 协议。
- `80 BC` 查询 PIN 信息的完整参数布局。
- 文件大小大于 255 字节时，`80 E0` 属性中的大小字段布局。
- 文件读写偏移非零时的边界行为。
- `SKF_RSAVerify` 的 raw 填充/字节序对齐。
- ECC 协商接口（`SKF_GenerateAgreementDataWithECC` 等）的设备命令
  细节。
- `SKF_ImportCertificate` / `SKF_ImportECCKeyPair` /
  `SKF_ImportRSAKeyPair` 的对象导入格式。
- 不同固件版本的命令差异。

如果要把本文档作为正式协议规范使用，应针对目标固件重新抓包验证上述
项目，并补充每个命令的完整请求/响应样本。
